# 装机流程仿真与调度工具

800 台服务器一次到货、全部插线网络启动装机,一天只装好一半。本工具把整条
装机链路做成可复现的仿真,回答现场最关心的四个问题:

1. **每台机器卡在哪一步、为什么卡** —— 按真实协议(POST → DHCP → TFTP →
   HTTP → 分区装机 → 重启)一步步走,同一类原因自动归并成片。
2. **上百台同时上电时哪个服务先崩** —— 地址池、引导文件服务、镜像服务、
   装机器各有一张容量表,仿真测出先饱和的那个,并反解出分批上电的节奏。
3. **装之前先核对硬件** —— 内存/硬盘的数量、型号、网卡固件、阵列控制器
   模式,和采购单及机型模板逐项比对,不符的标出来、拦下不装。
4. **工具的判断对不对** —— 场景里记着每台机器真实埋了什么,和工具的归因
   逐台核对,给出精确率/召回率;并对比"今天全上"和"核对+分批"的用时与
   失败数,以及排查负担。

```
┌─────────┐   ┌──────────┐   ┌──────────┐   ┌────────┐   ┌──────────┐
│  POST   │──>│ DHCP/PXE │──>│   TFTP   │──>│  HTTP  │──>│ 分区装机 │
│ 固件自检 │   │ 地址+引导 │   │ 引导程序 │   │ 安装镜像│   │ 阵列+分区 │
└─────────┘   └──────────┘   └──────────┘   └────────┘   └──────────┘
   本地问题      交换机/地址池     引导服务并发      镜像带宽      模板/物理盘
                                    └─────────── 共享服务容量 ───────────┘
```

## 快速开始

```bash
go run ./cmd/simctl                  # 命令行跑全套分析
go run ./cmd/simctl -serve :8080     # 起网页看板
go run ./cmd/simctl -json out.json    # 导出对比数据
go test ./...                        # 跑测试
```

命令行输出六段:场景与真值、装机前核对、服务瓶颈、方案对比、逐台归因核对、
分批节奏。网页看板把同样的数据做成可交互的:阶段墙、瓶颈排序、分批扫描、
归因矩阵、机柜成片问题、逐台交互日志。

## 场景

- **20 个机柜 × 每柜 40 台 = 800 台**,4 种机型(R760-A/B、R660-C、XR400-D),
  按真实比例 40/30/25/5 分配。
- **采购单**给出每种机型的应配内存、硬盘、网卡与固件下限。
- **机型模板**给出该机型必须落到的阵列级别(RAID1/6/10)、最少盘数、镜像与
  网卡固件要求。
- **共享资源**按约 500 台装机规模配置(地址池 512、TFTP 32 路、镜像 24 路
  /200MB/s、装机器 64 位)——800 台一次性上电必然打爆,这正是要暴露的。
- **确定性**:固定随机种子,同样的种子永远得到同一批机器、同一组问题。

### 埋入的问题(真值)

按真实比例埋,约每 8 台有 1 台带问题,外加整柜级的共因:

| 类别 | 例子 | 数量 |
|------|------|------|
| 机柜交换机 | CAB-03/14 启动 VLAN 未放行;CAB-07 会话上限 10 | 80+40 |
| 网卡 | 整批固件 18.4.0 低于要求;CAB-11 整柜如此 | 41 |
| 内存 | CAB-19 整柜 UDIMM 混插;少插一根 | 31+1 |
| 启动顺序 | 硬盘优先、外接设备优先、PXE 关闭 | 9+3+3 |
| 阵列 | 控制器停在 AHCI;残留试机阵列 | 8+6 |
| 硬盘 | SMART 预失效、型号错、少一块 | 5+4+2 |
| 镜像/脚本 | 镜像校验失败、服务端慢、kickstart 缺陷 | 3+1+1 |

## 设计要点

### 离散事件仿真(`internal/sim`)

- 事件堆按 (时间, 优先级, 序号) 排序,完全确定。同一时刻释放优先于超时,
  超时优先于主机步骤,主机步骤优先于新一波上电。
- 每个共享服务是一个**先进先出容量池**:请求拿不到槽位就排队并设超时,
  排队超时报出的原因与真实 PXE 客户端行为一致。
- 地址池是**信号量**(租约在装机期间一直占用),不是速率;容量小于同批台数
  时后到的排队,超过等待上限才判"地址池耗尽"。
- 镜像服务是**共享带宽**:每路拿总带宽的均分,上限是单路封顶——所以并发路
  数越多每路越慢,镜像阶段自然成为最慢的一环。
- 交换机是**每机柜的会话上限**:启动 VLAN 未放行或会话打满时,交换机会丢
  DISCOVER,归因据此区分"交换机问题"和"地址服务问题"。

### 归因(`model.FaultCode` 与阶段)

每台机器最多一个主因,在**第一次观测到协议不一致的那个阶段**归因:

- 上电 120s 无 DISCOVER → 启动顺序 / PXE 关闭 / 网卡固件(看 option ROM 输出)
- DISCOVER 有去无回 → 交换机 VLAN / 交换机会话 / 地址池耗尽 / 单机超时
- TFTP/HTTP 排队超时 → 对应服务饱和
- 建阵列失败 → 控制器模式 / 残留阵列 / 模板不适用 / 盘数不足
- 写盘掉线、ECC、脚本报错 → 硬盘/内存/脚本

### 装机前核对(`internal/audit`)

按"先物理、后交换机、再模板、最后 BMC"的优先级把问题分层:

- **物理**(开箱换件):内存/硬盘数量与型号、网卡型号、固件过低、盘数不足。
- **交换机**(改网络):整柜 VLAN 未放行、会话上限过低——一次发现、整柜生效。
- **模板**(改模板):模板要求的盘数/阵列级别采购的盘满足不了 → 整机型拦截。
- **BMC**(远程可修):启动顺序、PXE 开关、控制器模式、残留阵列。

`Remediate` 打开时,BMC 类问题在机器上电前经 BMC 下发修好,物理/交换机/模板类
仍然拦下不装。

### 容量分析与节奏(`internal/plan`)

不是拍脑袋算,而是**扫描仿真**:先用一次全量上电测出谁先满、排队多深;再对
每批 8…200 台各跑一遍,找出"零资源性失败"的批次规模,取用时最短的那个作为
建议节奏。节奏由镜像服务的单路时长和批大小反解出批间隔。

### 核对打分(`internal/report`)

- 把每台的真值和工具归因配对,**精确 / 近似(同症状不同根因)/ 错判 / 未判定
  / 误报** 五档。
- 近似档承认现实:同一症状(比如"没发起网络启动")可能来自启动顺序、PXE 关闭
  或固件过旧,协议层看到的是一回事。
- **排查负担**:把上电后"意外失败"按(阶段,原因)归并;≥3 台的算共因(修一处清
  一片,4 分钟),其余算个案(逐台排查,25 分钟)。这是区分"三天"和"一天"的关键。

## 代码结构

```
cmd/simctl/            命令行入口(分析 / 起服务 / 导 JSON)
internal/model/        阶段、故障码、真值、硬件、模板、采购单、事件
internal/spec/         800 台场景构建与确定性埋点
internal/audit/        装机前核对(物理/交换机/模板/BMC 分层)
internal/sim/          离散事件仿真引擎
internal/plan/         瓶颈排序与分批节奏(由仿真扫描反解)
internal/report/       汇总、对比、归因打分、排查负担
internal/webui/        网页看板(JSON API + 内嵌前端)
```

## 关于模型精度

这是流程与容量的仿真,不是固件仿真器:协议交互按真实时序与容量语义建模,
但不逐字节模拟 DHCP/TFTP 报文。数值(每阶段时长、每路带宽)是按 2024 年前后
两路机架服务器调的量级,可在 `internal/sim/sim.go` 顶部常量与
`internal/spec/spec.go` 的 `Pools()` 中调整。换了真实环境的实测值,瓶颈位置
和节奏会随之变化——这本来就是工具要支持的事。
